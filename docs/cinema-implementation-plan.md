# План реализации «Кинозала»

Статус: реализовано в рабочем дереве; локальная проверка описана ниже.
Production deploy и smoke-тест на VPS не выполнялись.
Документ сохраняет требования и план, по которому выполнена реализация.

## Task intake

### Scope

Добавить изолированный каталог «Кинозал» для готовых локальных видео: создание
записи с названием, показ ожидаемого пути файла, ручная передача на VPS,
воспроизведение и удаление записи вместе с файлом. Просмотр только после входа;
изменения только администратором. Текущая задача — реализация описанной функциональности,
тесты и эксплуатационная документация, без production deploy.

### Non-goals

Загрузка через браузер, действие «Подключить файл», серверное кодирование,
извлечение аудио, получение метаданных, постеры, описание, год, ввод длительности,
RSS, yt-dlp, автоматическое наблюдение за каталогом, фоновые задачи и интеграция
фильмов в существующие фиды. Новые npm/runtime-зависимости не нужны.

### Touched surfaces

SQLite, handlers/routes, pages/bakers/parts, существующий
плеер, приватная навигация, RU/EN-переводы, тесты, создание каталога и документация
эксплуатации. Конкретные точки входа перечислены ниже.

### Acceptance criteria

Полный перечень в конце документа; продуктовых отклонений нет.

### Verification

HTTP/file lifecycle, browser tests, typecheck, lint, format и server coverage по
разделу «Проверка». VPS smoke — N/A до отдельно разрешённого production deploy.

## 1. Обязательные требования пользователя

1. «Кинозал» выглядит как отдельный специальный канал/раздел сервиса, но его
   записи **вообще не участвуют в существующих фидах**: «Все», «Готовое»,
   «Загрузки», теговые ленты, обновления фидов и их API.
2. Каталог, записи, плеер и файлы доступны только залогиненным пользователям.
   Гостевого доступа нет и включить его нельзя. Не добавлять guest-visible toggle.
3. Создание и удаление — только администраторам. Обычный пользователь смотрит.
4. В форме добавления ровно одно содержательное поле: обязательное название.
   Служебные UID/время создаются сервером; это не поля формы.
5. Администратор самостоятельно подготавливает файл для браузера и вручную
   передаёт его на VPS по SSH/rsync. Приложение не принимает байты видео через API.
6. Запись связывается с файлом по сгенерированному UID, не по названию.
7. Сервер сообщает, где ожидает файл. Кнопки «Подключить», импорта, регистрации
   файла и сохранённого статуса готовности **нет**. Наличие конечного файла
   определяет доступность при каждом чтении.
8. До появления файла показывать «Ожидает файл», после — «Смотреть».
   Для обновления уже открытого каталога достаточно перезагрузить страницу.
9. Файл отсутствует/непригоден для выдачи — сервер не отдаёт его, возвращает 404.
   Запись при этом не удаляется.
10. Администратор может удалить запись вместе с конечным и незавершённым файлом.
11. Автоочистка диска не должна удалять фильмы «Кинозала».

Эти требования приоритетнее предварительных идей: не добавлять локальные фильмы
в общую `videos`, если единственная причина — участие в «Готовом»; такого участия
нет. Не переносить сюда смысл существующего канала «Загрузки».

## 3. Данные и изоляция

### Рекомендуемая модель

Отдельная таблица `cinema_videos`:

```text
uid         TEXT PRIMARY KEY
title       TEXT NOT NULL
created_at  TEXT NOT NULL, UTC timestamp по существующему соглашению
```

Публичный UID генерировать криптографически, в формате существующего UID-валидатора
(сейчас `randomBytes(12).toString('base64url')`, 16 символов). Не использовать
YouTube ID, имя фильма или исходное имя файла. Коллизии обработать ограниченным
повтором генерации. UID не переиспользуется после удаления.

Почему отдельная таблица: каталог полностью изолирован; изменения обязательного
`youtube_id`, CHECK-ограничений и всех SQL-фидов не нужны. Старые записи,
статистика и схема YouTube-каталога остаются нетронутыми. Не добавлять фиктивные
YouTube ID, новый channel ID с предположением «2 свободен» или общий media registry.

«Кинозал» в UI — специальный неизменяемый пункт с адресом `/cinema`, а не обычная
редактируемая YouTube-строка `channels`. Он существует и при пустом каталоге.
Это техническая рекомендация плана, а не дополнительное требование пользователя
к SQL-схеме; если текущий код изменился и решение нужно пересмотреть, сохранить
все продуктовые требования и объяснить отклонение в описании задачи.

DAL, например `src/lib/cinema.ts`: создание, поиск по UID, пагинированный список,
удаление записи; небольшие функции построения пути и проверки файла. Не делать
несколько абстрактных слоёв для CRUD одной таблицы.

### Доступность

Не хранить `ready`, `ready_at`, `file_path`, длительность и импортируемые метаданные.
Путь детерминирован. При построении страницы получить ограниченную страницу записей
и проверить только её файлы, не сканировать весь медиакаталог.

Доступный фильм — конечный непустой обычный читаемый файл по ожидаемому пути.
Симлинки, каталоги, `.part` и нулевой файл не считаются готовыми. `ENOENT` — нормальное
ожидание файла; прочие ошибки логировать без утечки локальных путей пользователям.
Перед выдачей bytes повторять проверку независимо от состояния карточки.

Порядок: `created_at DESC, uid DESC`, явная пагинация с ограниченным page size
(ориентир — существующие 42 записи). Никакого infinite scroll. Повторяющиеся названия
допустимы: записи различаются UID.

## 4. Файловый контракт и ручная загрузка

```text
${MEDIA_DIR}/cinema/<uid>.mp4.part  # передача не завершена; приложение игнорирует
${MEDIA_DIR}/cinema/<uid>.mp4       # конечный файл; доступность определяется здесь
```

Промежуточный `.incoming` не нужен. Не принимать пути/имена файла через форму или
JSON. Использовать только валидированный UID и фиксированное расширение `.mp4`.
Название фильма никогда не участвует в пути, shell-командах и HTTP-заголовках.

Формат первой версии: MP4, подготовленный администратором для браузера
(рекомендация H.264/AAC, faststart). Расширение не доказывает кодек или целостность:
приложение этого не обещает. Не устанавливать ffmpeg/ffprobe и не запускать
yt-dlp/транскодирование/генерацию thumbnail.

### Инструкция, отображаемая администратору

После создания и для каждой существующей записи показать UID, ожидаемый путь и
краткую последовательность передачи. В первой версии достаточно текста/`code`,
без отдельного мастера и clipboard-фичи. Обычным пользователям серверный путь не
показывать, включая baked JSON.

Пример документации для стандартного `/opt/vidium` (заменить `UID`, SSH target и
локальный путь; фактический корень брать из `MEDIA_DIR`, не хардкодить в runtime):

```bash
rsync -avP './film.mp4' root@VPS:/opt/vidium/media/cinema/UID.mp4.part
```

Только после успешного завершения передачи выполнить на VPS:

```bash
chown vidium:vidium /opt/vidium/media/cinema/UID.mp4.part
chmod 0640 /opt/vidium/media/cinema/UID.mp4.part
mv -n /opt/vidium/media/cinema/UID.mp4.part /opt/vidium/media/cinema/UID.mp4
```

Это пример для существующего root-based workflow, не требование открывать root SSH
или выдавать shell сервисному пользователю. Для обычного SSH-оператора описать
вариант с согласованными правами/sudo. Пароли, SSH-host и ключи в приложении не хранить.
Существующий конечный файл не перезаписывать: при `mv -n` убедиться, что `.part`
исчез, а не считать один exit code доказательством переноса.

Почему `.part`: если писать сразу в `.mp4`, приложение увидит недокачанный фильм.
Переименование в том же каталоге/файловой системе атомарно. После него достаточно
обновить страницу: отдельного HTTP-подключения файла нет. После обрыва можно повторить
rsync; объяснить, что это не перекодирование и rename не делает вторую копию фильма.

### Каталог и эксплуатация

- Каталог `cinema/`: `vidium:vidium`, mode `2750`; конечные файлы `0640`.
  nginx (`www-data`) читает через существующую группу `vidium`.
- Обеспечить создание каталога на свежем хосте и для существующей установки:
  небольшой идемпотентный шаг и явная инструкция, без запуска полного setup на VPS.
- Корень и родительские каталоги должны быть доверенными, не симлинками и не
  доступны для записи веб-пользователям. Валидировать UID до filesystem-вызовов;
  не следовать symlink на файле. Не обещать защиту от доверенного SSH-оператора,
  меняющего файлы между проверкой Node и открытием nginx.
- Не добавлять `cinema/` в автоочистку. Не менять её политику ради фильмов.
- Объяснить: фильмы и `.part` могут заполнить диск; существующий индикатор диска
  остаётся средством контроля, удаление незавершённых передач вручную/через удаление
  соответствующей записи. Не вводить новую систему квот или уборки orphan-файлов.
- Обычный deploy сохраняет весь `media/`; проверить, что правило сохраняется.

## 5. HTTP, авторизация и плеер

Рекомендуемые маршруты (окончательные имена держать согласованными в коде/доках/тестах):

| Метод/путь | Доступ | Поведение |
| --- | --- | --- |
| `GET /cinema?page=N` | session | Каталог; отсутствие session — штатный redirect на login |
| `GET /cinema/v/:uid` | session | Существующий video player для доступного фильма; иначе 404 |
| `GET /cinema/media/:uid` | session | Проверить запись и файл; `X-Accel-Redirect: /protected_media/cinema/<uid>.mp4`, `video/mp4`; иначе 404 |
| `POST /api/admin/cinema/video` | admin + CSRF | JSON `{ title }`; создать запись, вернуть UID и данные для admin-инструкции, 201 |
| `POST /api/admin/cinema/video/delete` | admin + CSRF | JSON `{ uid }`; удалить файл(ы) и запись |

Для приватного media endpoint без session возвращать 404 без `X-Accel-Redirect`,
не HTML login page вместо видео. Для admin API использовать текущие helpers:
штатные 401/403, CSRF, ограничение body, JSON-ответы. Невалидный JSON/UID/title — 400.
Проверить фактические соглашения существующих helpers перед реализацией.

Название: строка после trim, не пустая, разумный явный максимум (рекомендация 300
символов). Проверка на сервере обязательна; UI повторяет ограничения. Всё
пользовательское содержимое экранировать, baked JSON сериализовать существующим helper.

Защита не ограничивается новыми URL: UID фильма не должен раскрывать его через
`/v/:uid`, `/a/:uid`, `/media/v/:uid`, `/media/a/:uid`, `/t/:uid`, `/api/status`,
`/api/since`, `/api/feed/cards` и `/api/download`. При отдельной таблице существующие
запросы обычно ничего не находят; подтвердить тестами. Гостям не отдавать названия,
UID, локальные пути или HTTP media redirect ни через какой endpoint.

nginx: существующий internal alias на весь `MEDIA_DIR` уже покрывает `cinema/`.
Не добавлять публичный alias `/cinema/` на файлы! `.part` не имеет доступного media
маршрута. На VPS проверить, что `/protected_media/` действительно internal.

### Переиспользование существующего плеера

Не копировать весь browser player. Добавить небольшой cinema-specific server baker
либо явную ветку в существующий baker; page renderer собирает тот же player part.
Handlers сохраняют HTTP-авторизацию, baker читает запись и строит state.

Проверить и адаптировать следующие поля/действия:

- `kind = video`, собственный `mediaSrc`, title, стабильный cinema-specific instance ID
  и resume key; не пересекать localStorage-позиции с YouTube.
- Ссылка «Кинозал» ведёт на `/cinema`, не на `/channel/0` и не на фиктивный channel ID.
  Передать явный безопасный внутренний href, сохранив старое поведение YouTube.
- Нет аудиорежима, thumbnail-fetch к `/t/:uid` и списка глав. Без постера video
  показывается штатно; optional artwork корректно обработать в Media Session.
- Длительность берёт браузер из media metadata; в БД её не вычислять и не сохранять.
- `shareAvailable = false`: публичной ссылки нет. Обычный приватный URL можно открыть
  после входа, но не превращать это в guest-sharing.
- Статистика кино в первой версии вне scope: не отправлять `/api/play` для этих
  записей и не расширять FK-статистику YouTube. Добавить явную capability/boolean
  в state, сохранив прежнюю отправку для YouTube. Не оставлять фоновые 404-запросы.
- Сохранить работающие управление, перемотку, громкость, скорость, resume,
  Media Session и sleep timer; изменения DOM по правилам parts.

## 6. UI и frontend-контракты

- Видимый только после входа специальный пункт «Кинозал» в существующей навигации.
  Он не имеет тегов, RSS, автоскачивания, гостевой видимости и формы переименования
  обычного канала. Не включать его в массив данных, который ожидает numeric channel ID.
- В самом каталоге: название раздела, пустое состояние, пагинация, записи с названием
  и «Ожидает файл»/«Смотреть». Без фиктивных постеров и нулевой длительности.
- У администратора: форма с названием, инструкция загрузки по UID и кнопка удаления
  для каждой записи, в том числе ещё не загруженной. Инструкция остаётся доступной
  после перезагрузки, а не только в ответе создания.
- После создания/удаления достаточно загрузить заново текущую страницу каталога;
  корректно обработать удаление последней записи последней страницы.
- Отдельный `cinema-page` part допустим: у него иной контракт и нет download/polling
  существующего feed-card-pager. Переиспользовать shell, стили и player, не строить
  framework и не менять общую карточку YouTube без необходимости.
- Backend page data загружает baker; page renderer отдаёт shell, flat baked JSON
  по стабильным instance ID и mount scripts. Не делать серверный HTML body.
- Browser `index.js` не импортирует baker. Event/async handlers вызывают `part.set`,
  DOM меняется только в `handlers.state[*]`. Без inline event attributes.
- Коллекции менять через `items`/`cards`; targeted patch-поля нужны только при
  реальной необходимости, не использовать microState/MacroState как command bus.
- Новые тексты добавить в RU/EN. «Кинозал» — русское название, английское — Cinema.

## 7. Удаление и сбои

Администратор подтверждает «Удалить запись и файл» с названием и предупреждением
о необратимости. Сервер берёт только UID, сам строит два точных пути; никакого glob,
рекурсивного удаления каталога или пути из JSON.

Порядок операции:

1. Проверить admin, CSRF и UID.
2. Удалить `<uid>.mp4` и `<uid>.mp4.part`; `ENOENT` считать допустимым.
3. Только после успешных файловых операций удалить запись из `cinema_videos`.
4. Вернуть успех; повторный вызов безопасен, отсутствие записи/файлов не ошибка.

Ошибки `EACCES`/I/O не проглатывать: вернуть ошибку без ложного успеха, запись оставить
для повтора. Если один файл уже удалился, откат файлов не обещать; проверка
доступности при следующем чтении отражает действительность. Если процесс упал
между unlink и удалением строки, повтор завершает операцию. SQLite и filesystem
не образуют общую транзакцию; не заявлять атомарность всей операции.

Чтение/проверка не блокируют файл навсегда: если его удалили после проверки, возможен
404 от nginx. Уже начатая передача может завершиться с открытым файловым дескриптором;
удаление не гарантирует немедленное прерывание текущего просмотра.

SSH-загрузка не координируется HTTP-сервером: **перед удалением записи администратор
останавливает её передачу**. Иначе внешний rsync/mv может создать orphan-файл уже после
удаления. Документировать ограничение, не изобретать lock-протокол с внешним rsync.
Приложение не отдаёт orphan-файл без существующей строки в БД.

Не переиспользовать YouTube delete endpoint с поддельным `youtubeId`. Отдельная
таблица означает, что существующая админка не перечисляет фильмы как скачанный
YouTube-кэш; управление фильмами находится в «Кинозале».

## 8. Этапы реализации

1. **Повторная разведка и intake.** Прочитать обязательные docs и код, проверить
   рабочее дерево. Скопировать intake в описание задачи/PR; перечислить отклонения.
2. **Данные и файлы.** Идемпотентно создать `cinema_videos`, DAL, UID/path validation,
   безопасную проверку доступности, создание каталога. Не мигрировать общую `videos`.
3. **HTTP.** Добавить приватные страницы/media и admin CRUD API, CSRF и ошибки.
   Покрыть HTTP-тестами доступ всех трёх ролей и file lifecycle до UI.
4. **Каталог.** Добавить part/baker/page, приватный nav link, форму названия,
   пагинацию, постоянную admin-инструкцию и подтверждение удаления; RU/EN.
5. **Плеер.** Переиспользовать текущий part с минимальным явным контекстом,
   убрать cinema-зависимости от `/api/play`, YouTube channel/thumb/share.
6. **Регрессии и безопасность.** Подтвердить изоляцию от всех фидов/API/worker,
   отсутствие автоочистки, корректную обработку symlink, ошибок и повторов.
7. **Документация и выпуск.** Обновить `SETUP.md`, `docs/server-runtime.md`,
   `docs/deploy.md`; описать создание каталога для существующего VPS, ручную загрузку,
   права, `.part`, удаление и ограничения. Пройти quality-checks и smoke-тест.

Новые модули должны оставаться предметными (`cinema`), а не общими layers для
media providers. Не добавлять npm-пакеты, worker jobs, watchers, новые демоны,
systemd units, транскодирование или отдельные env-настройки без реальной причины.

## 9. Проверка

### Автоматические тесты

Использовать текущий harness `scripts/tests/`, изолированные временные DB/media и
настоящие HTTP-запросы по принятому в проекте шаблону. Не трогать production media.

- Bootstrap новой и существующей БД, повторный запуск: таблица появляется один раз,
  существующие каналы/видео/статистика и их counts не меняются.
- Admin создаёт запись; пустое/пробельное/слишком длинное/нестроковое название,
  malformed JSON, XSS-название, отсутствие admin/session/CSRF.
- Одинаковые названия допустимы; UID различаются и валидны; название не влияет на путь.
- Без файла и с одним `.part` — ожидание, нет `X-Accel-Redirect` и media 404.
- После rename непустого файла — «Смотреть»; media redirect указывает только на
  internal cinema path. После внешнего удаления — снова ожидание/404 без изменения БД.
- Нулевой файл, каталог вместо файла, symlink, traversal/encoded traversal, invalid UID,
  произвольные пути в JSON, известный UID без строки БД не дают доступа к файлам.
- Guests не получают каталог, строки/названия/UID, player или media через новые и
  старые endpoints. User смотрит, но не создаёт/удаляет. Admin может управлять.
- Фильм отсутствует во всех общих фидах/ready/manual/tags/since/status/feed cards,
  не скачивается через `/api/download`, не создаёт jobs и не включается в RSS.
- Автоочистка удаляет подходящий тестовый YouTube-кэш, но сохраняет cinema `.mp4`
  и `.part`, даже при высоком использовании диска.
- Удаление с обоими файлами, без файлов, повторное удаление, ошибка unlink,
  частичный сбой: нет ложного успеха, возможно повторить, строка не теряется раньше времени.
- Пагинация/пустое состояние/последняя страница после удаления; server path отсутствует
  в HTML/baked JSON обычного пользователя.
- Browser: создание через одно поле, статус ожидания, появление «Смотреть» после
  обновления, удаление с подтверждением, отсутствие admin UI у user и cinema у guest.
- Browser player: нормальная работа существующих функций; нет cinema-запросов к
  `/api/play`, `/t/:uid`, download/audio endpoints и нет публичного share.
- Регрессия существующих YouTube-карточек, плеера, статистики, гостевого доступа и API.

Команды из текущего `package.json`:

```bash
node --run check
node --run lint
node --run format:check
node --run test
node --run test:browser
node --run test:coverage:server
```

Coverage-команда сейчас явно перечисляет HTTP test-файлы через `http-*.test.mjs` и
отдельные suite. Новые runtime tests назвать/подключить так, чтобы они действительно
попали в нужные проверки; не ослаблять coverage thresholds. Browser использует
системный Chromium, при необходимости `VIDIUM_CHROMIUM_PATH`.

### Smoke-тест на VPS

Только после разрешённого production deploy из проверенного master по текущим docs:

1. Сохранить backup БД; добавление новой таблицы не требует переписывания `videos`.
   Создать cinema dir и проверить владельца/modes для существующего хоста.
2. Проверить login, обычный feed и работоспособность server/worker после релиза.
3. Admin создаёт тестовую запись; user видит ожидание, guest не видит каталог.
4. Загрузить небольшой реально воспроизводимый MP4 в `.part`; видео ещё недоступно.
5. После прав и rename обновить каталог, воспроизвести, перемотать; проверить Range
   и заголовки через nginx. Node unit-тест с фиктивными bytes этого не доказывает.
6. Убедиться, что public `/protected_media/cinema/...` закрыт, user media работает,
   guest media не выдаёт bytes. Проверить стандартный cache policy приватного media.
7. Удалить через UI; запись и оба имени файла отсутствуют, повтор безопасен.

nginx reload нужен только при реальном изменении конфига; стандартный internal alias
уже подходит. Не запускать setup/force-nginx и не перезаписывать Certbot-конфиг ради
этой фичи. Не выполнять deploy или SSH-команды автоматически в рамках реализации.

## 10. Итоговые acceptance criteria

Отметки ниже подтверждены локальными тестами и осмотром реализации/конфигурации;
они не заменяют отдельный production smoke-тест из раздела 9.

- [x] «Кинозал» существует как отдельный раздел, доступный только после входа.
- [x] Фильмы не попадают ни в один существующий фид или его API даже для admin/user.
- [x] Единственное поле создания — название; admin получает UID и ожидаемый путь.
- [x] Нет browser upload, кнопки подключения, кодирования и фонового импорта.
- [x] Связь БД/файл — UID; готовность определяется filesystem, не сохранённым статусом.
- [x] `.part` не воспроизводится; atomic rename делает завершённый файл доступным
      после обновления страницы. Исчезновение файла снова даёт ожидание/404.
- [x] Любой залогиненный user смотрит готовый фильм; только admin создаёт/удаляет.
- [x] Ни один маршрут не раскрывает гостям кино-данные или bytes; публичного sharing нет.
- [x] Работает существующий плеер без кино-запросов к YouTube-only API/thumbnail.
- [x] Удаляются запись и оба точных имени файла; отсутствие файла и повтор безопасны,
      реальные файловые ошибки не маскируются.
- [x] Нет symlink/path traversal, произвольных файловых путей и утечки admin-пути user.
- [x] Автоочистка и deploy не удаляют cinema files; права совместимы с nginx/systemd.
- [x] Новых runtime-зависимостей нет; YouTube-поведение и данные сохранены.
- [x] Тесты и quality checks выполнены; результат/ограничения записаны в задаче/PR.
- [x] Инструкция на свежий и существующий VPS описывает `.part`, права, rename,
      удаление, место на диске и запрет удаления во время SSH-передачи.
